# Whole-request and server-command timing: exploratory03

This is a new performance exploration after feasibility01/02, not a preregistered confirmatory evaluation. The previous finite outcomes informed the chosen contrasting coefficient settings, which are disclosed. No old result or failed attempt is rerun to improve its verdict. We test the practical limitation of the exact kernel-resource result: reducing protected SHA1Transform invocations may lower server-command duration or other-client delay while increasing foreground work/transfer/completion time. No direction of change is assumed.

Use only the unmodified Valkey8.0.2 binary from manifest01. Compile its unmodified SHA1 source into a plain outside client library with no diagnostic counter and record its exact source/build hashes. The native instrumented binary/library from refresh02 are not used for timing. Keep redis.sha1hex computation and whole publication semantics unchanged. Use a private Unix socket, TCP disabled, no persistence, one foreground client, one admitted writer client and one periodic PING client. Hardware/OS and all process configuration are recorded. This is one-host performance, not network/cloud latency or an SLA guarantee.

Fix three components with compression weights(1,2,3)*scale and lengths64*w-9. Scales4096,16384,65536 are fixed before timing. Footprints are singletons. The retained-refresh prepared protocol permitsq3 validations, thus at most4 foreground wire commands including its initial HMGET; direct uses1. Compare direct full-server publication, immediate prepared repair, reject-dirty-until-last, and the compiled unaware minimum-regret policy. Coefficient triples are(alpha,beta,rho)=(1,0,scale),(1,1,0),(4,1,scale),(1,4,scale). The resource parameter rho is not inferred from a measured latency and the objective is not called elapsed time. Compiler/source construction cost is recorded separately.

Four fixed update scenarios: none; the smallest component written once; largest component written once; all three components each written once. Writes occur after the initial snapshot/prepare and before the first validation, or before direct's only validation. There are no later writes in these timing cases. Every compared policy therefore experiences the same exact external-write count0,1,1,3, and the same initial/updated payload contents, even if it completes on a different validation. External update data and JSON are constructed before timing; the writer's actual command round trips occur during the foreground request and are separately measured as interference. Repeated full invalidation remains in the exhaustive semantic/resource02 study and is not mixed into these timing comparisons.

Eight randomized paired blocks per(scale,coefficients,scenario), each containing all four policies in a seeded permutation (seed20260910). One disclosed warmup per policy per cell precedes the eight measured blocks. Total cells48, measured requests1536 and warmups192. Preserve every request, failure, timeout and invalid row. Per-request cap15seconds and overall driver cap900seconds; stop and retain partial results if exceeded. Every owned process/socket/thread must close in finally.

Measure: foreground request wall time from before initial snapshot (or direct path) to final publication result; outside client hash time; each foreground command round trip; encoded request/response wire bytes; writer command duration; and exact resource vector(L,W,Qwire) inferred from the already checked unmodified source paths and confirmed by final digest/version oracle. Valkey's built-in SLOWLOG at threshold0 supplies whole server-command execution durations, including Lua/guard/copy/encoding work within commands. Report maximum and sum of foreground HMGET/EVALSHA durations, not merely the completing Lua call. SLOWLOG omits some event-loop/network work, so its maximum is not claimed to bound all blocking. All modes use the same slowlog configuration.

A single companion client sends PING repeatedly with an intended2ms interval, one outstanding request at a time. Retain timestamped RTT samples, actual sample counts and interarrival gaps. Report per-request maxima and distributions across paired blocks; different foreground durations produce different ping counts and no equal-arrival-rate or universal tail-latency guarantee is inferred. Include samples initiated while the foreground request is active, and wait for an outstanding sample to finish. Probe startup/stop is excluded from foreground timing but declared as test overhead.

Pair ratios within the same cell/block against direct and immediate prepared repair. Use fixed-seed bootstrap over the eight block-level paired ratios (10000resamples, arithmetic/geometric ratio summary stated explicitly) and show confidence intervals with the small sample limitation. Do not select only improved cells, collapse coefficient/input families into invented independent applications, or let latency override correctness failures. All48cells and all resource/work increases remain visible. A stronger final performance claim would need a later fixed evaluation and further deployment diversity; this study decides whether this native path merits continued focus.
