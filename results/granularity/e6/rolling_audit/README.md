# Rolling(2,1) with one audit handoff

The literal v1 candidate extends the fixed Rolling(2,1) witness with one old/new audit rule pair. Physical local state counts and existing transitions are preserved; global `log_old` and `log_new` self-loops are added at every local state as an external log-sink abstraction. The old and new audit testers require their corresponding log before the next service event. This checks finite event order, not durable log delivery or correctness of a particular logging system.

There is exactly one interval requirement: the product of availability (at least one replica ready) and audit activation coverage (old active or new active). No precedence edge forces the order. Stopping the old audit before starting the new one enters the interval error; starting the new one first permits overlap. The new audit initializes to unlogged on all nine versioned physical products. There is no hidden activation guard. Old and new endpoint closed loops each have two reachable states, corresponding to unlogged/logged. Controller alphabets explicitly include all ordinary actions so missing labels do not introduce unintended external stuttering.

The preregistered expectations are fine WIN, transfer-merged LOSS, boundary-merged WIN, both-merged LOSS and Direct-Full fine WIN. With only one start and one stop, boundary merging is a renaming. This candidate deliberately reports that null result and does not add an opposing-order rule to manufacture boundary sensitivity. Policy(2) is a separate example. A candidate six-transition completion is start-new, stop-old, transfer-1, ready-1, transfer-2, ready-2; returned ranks and actual certificate paths are measured separately.

`design/v0_precedence_only/` retains the first unexecuted proposal. It was replaced before generation or measurement to express the requested gap prohibition through an interval tester and give the audit rules a nontrivial event-order meaning. The version change is a specification correction, not a response to a result.

`gen_rolling_audit.py` creates four explicit contracts and a fixed eight-cell schedule under `v1/`. `validate_rolling_audit.py` independently checks endpoint products, the exact append-only physical extension, the full initializer domain, monitor effects and generated grouping. The common frozen E1 adapter/harness is reused unchanged. The fine input's three E1 merge runs compare all reachable Post behavior against the corresponding generated contracts. Every checked WIN certificate is additionally inspected for physical readiness and audit coverage; every LOSS is checked for an immediately unsafe all-at-once transfer.

Outputs: `v1/summary.csv` and `v1/tables/results.csv` retain all eight cells. `rolling_audit_summary.json`, `generated_comparisons.csv`, `certificate_checks.json`, `mechanism_reasons.csv`, `completion_paths.json` and `table_rolling_audit.tex` provide the paired interpretation and reusable data. A completion path is one example from the returned policy, not a claim that it is the only execution. The original Rolling input is copied byte-for-byte under `v1/reference/` and its SHA is recorded in every generated input.

This model is inspired by the Rolling availability practice already documented in the base example and an explicitly stated continuous-audit contract. It is not a reproduction of a particular deployment or an empirical claim about logging implementations.
