# Matched-call-cap collateral blocking: exploratory, before measurements

The question is whether the counted protected-work separation at B=r is visible in the wait of an actual concurrent operation on a different key in the same ConcurrentHashMap bin. This is an authored, controlled mechanism experiment, not a workload prevalence study, a latency guarantee, or a calibration of worst-case execution time. Prior Java experiments and Claude's suggestion are known; this packet's timing outcomes have not been run.

Four dependent jobs form a chain, with whole-kernel iteration weights (1,2,3,5). A kernel uses its own immutable input and the exact completed predecessor result. Loop scales are fixed to 64, 2048, 65536, and 2097152 iterations per weight before timing. Policies have a global failure allowance r in {0,1,2}. They prepare/validate until r cheap failures, then either compute fresh inside every completing callback (two modes), or prepare outside and reuse/recompute inside the callback (three modes). The selector receives only dependencies, the mode family and r; it receives no writer budget or scale. An external writer forces exactly r failures of job zero, then performs no more writes. This is the constructive B=r separation, not a random contention distribution. Both policies must have Q=4+r, W=(11+r)*scale, and the same completed outputs; L is 11*scale and zero, respectively. Q counts publication/validation calls, W all kernel iterations, L the sum of iterations under protection, not the longest critical section. Initial map loads, writer actions and the unchanged-value probe are separately recorded, outside these foreground counters.

Each completing callback signals a persistent probe thread. The probe timestamps immediately before publishing a readiness latch and calling compute on a different key. The foreground waits for readiness, then executes its callback body. The probe returns its unchanged input and creates no invalidation. In the same-bin layout, all four job keys and the probe key collide in the initial 128-bin table. The disjoint-bin layout moves only the probe key to a different bin. Both layouts retain the same latch, instrumentation and foreground policy. The probe's issue-to-callback-entry time includes OS scheduling and synchronization overhead. The disjoint control measures these effects without the shared bin lock; it is not subtracted from samples. Hooked foreground elapsed time includes instrumentation and is not an uninstrumented throughput estimate. No sleep or yield is inserted into the kernel.

Primary measurement: the sum of the four probe issue-to-entry waits per invocation. Secondary measurements: maximum individual probe wait, individual waits/operation durations, foreground total time, callback hold intervals, kernel time outside/inside protection, setup time, wall time and exact Q/W/L. All intervals use System.nanoTime. Raw records preserve per-job timing and output checksums, ordering, policies, failures and outcomes. The same-bin trace must show probe entry after the foreground callback body; kernels must not execute under protection in successful cached callbacks. A probe timeout, missing job, counter mismatch or output mismatch fails that unit; no timing outliers are dropped.

The fixed evaluation has 3 independent JVM forks, each with 30 repetitions of every (scale,r,layout,policy) cell: 4320 invocations, 2160 paired comparisons, 17280 probes. Warmup uses 10 additional repetitions of every cell in each fork, identified as warmup and kept in separate raw files, never added to measurement denominators. Within each repetition, pair order and within-pair policy order are shuffled by a fixed seed and recorded. JVM flags: -Xms512m -Xmx512m -XX:+AlwaysPreTouch, otherwise default compiler/GC. Forks run serially. Each child is bounded at 360 seconds; each probe/writer await is 3 seconds. The runner reserves every planned unit in advance. All SUCCESS/FAILURE/TIMEOUT/INVALID units and missing units after a process failure are retained. No rerun of a measured unit. A compilation or smoke-test defect is a development outcome and must be retained before any changed evaluation version. The smoke test is semantic only and its timings are not used in summaries.

Analysis fixed before results: for each scale/r/layout, report per-fork and pooled median sums, median paired difference (two minus three), ratios of medians, and the 95% percentile bootstrap interval of the paired median difference using a fixed seed and 20000 resamples. Bootstrap within the pooled invocation pairs is descriptive and does not make three JVMs into thousands of independent environments. Also report the range of per-fork median differences; 30 repetitions do not establish a tail-latency bound. Show all 24 cells, including small-kernel and disjoint controls, and no selected threshold of practical significance. A positive interval indicates an observed conditional difference, not a universal runtime guarantee. If controls show comparable effects, attribution to bin contention remains uncertain. Native API conformance must pass before drawing timing conclusions; statistical summaries cannot repair semantic failures.

The scope does not include industrial adoption, human impact, total application performance, arbitrary scheduler fairness, variable kernel work or worst-case machine timings. These limitations do not erase the experiment: it tests the proposed resource distinction against actual collateral blocking under an explicit contention opportunity.
