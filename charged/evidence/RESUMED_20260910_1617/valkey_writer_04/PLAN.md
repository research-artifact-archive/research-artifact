# Stronger writer-maintained comparison, exploratory04

Fixed before implementation and execution, 2026-09-10. The earlier hash-manifest timing study used a fixed SHA1 transform. A cooperative writer can therefore compute the updated digest outside the server and commit it with the new payload/version. This is an available stronger design, not a weaker retry policy. Its setup and every subsequent writer hash must be charged. This experiment decides whether the fixed-hash Valkey case supports a useful algorithm claim beyond moving computation between participants. It does not manufacture a use case in which writer cooperation is impossible.

Compare three complete designs: direct reader hashes everything atomically; the current compiled retained-refresh reader; and writer-maintained digests with a single atomic reader publication. All publish a vector of versions and their current payload SHA1 digests at a linearization point. Use the same admitted singleton writer footprints, initial bytes, update bytes, order, and successful-call assumptions. The maintained writer commits payload, new decimal version and its computed digest together. The client computes that digest honestly from the exact supplied immutable payload; the server does not pretend that accepting a supplied digest proves its correctness against an untrusted writer.

Use the existing unmodified Valkey8.0.2 binary and plain unmodified C SHA1 library. Introduce one shared RESP writer script for all designs, avoiding the earlier JSON payload encoding. Its base mode changes payload/version; maintained mode additionally stores the digest. This is a changed writer implementation, so results are not paired reruns of timing03. Its decimal increment rule is identical to the retained writer source. All new sources and the schedule are hashed before execution.

Fixed cells: component weights (1,2,3)*scale for scale4096 and16384; number of reader operations R in {1,8}; four update scenarios: no writes; smallest component once per read; all three components before the first read only; all three components once per read. Writer calls occur after compiled preparation and before its first validation, or immediately before the sole reader call in the other designs. Thus all designs see the same result at each numbered read. The known schedules are test-driver inputs and are not supplied to the policy. Compiled uses q3, alpha4,beta1,rho=scale, and the existing compiler unchanged. No writes follow the first validation in this experiment; this deliberate inherited limitation prevents claims of a new adversarial-policy stress test.

There are16cells. For each cell use six randomized paired blocks of the three designs, plus one warmup of each design, with seed202609101804. This gives288 measured mixed traces and48 warmups. Also run12 small semantic smoke traces before timing: one read, four update scenarios, three designs. Preserve every failure, timeout, invalid trace and unexecuted case. Bound the complete run at600seconds, each command at15seconds. Close all owned processes/connections in finally. No companion PING is included: the question here is the strongest cooperative baseline and complete accounting, not a tail-latency claim.

Common test data construction and initial payload/version HSET are outside the timed mixed trace and reported as setup. For maintained mode, additional initial hashing of all components and installation of digest metadata are inside the trace and charged explicitly. Every maintained update computes its new digest inside the timed writer operation after the common immutable payload is available. All modes' writer round trips and serialized command transfer occur inside the mixed trace. Additional maintained metadata construction and command serialization are charged. Digests used solely by the final oracle are precomputed outside measurement and never passed to the foreground or writer implementation.

Record per reader and writer: elapsed round trips, server SLOWLOG durations, outside hash duration, wire bytes, and exact transform work. Record full mixed-trace elapsed time from before maintenance build (when present) through the last reader publication; build time/work/wire separately; foreground reader elapsed excluding intervening writer operations by summing its own command and hashing intervals; read latency including synchronous writer interference separately. Report source-compilation/library costs from existing receipts. Resource totals distinguish foreground L/W, writer transform work, initial maintenance work, total transform work, server commands, and all measured-participant wire bytes. Maximum server command includes readers, writers and initial maintenance metadata installation. It is not a bound on all event-loop blocking.

The exact work check is direct total=R*P; maintained total=P+sum_writes h(footprint); compiled total=sum_read foreground W. Initial digest maintenance must not be amortized away silently. Six-block paired ratios/medians are exploratory descriptions on one host. All16cells are reported with R, total updates and total update weight, including when maintenance loses on time/work. No statistically independent applications are inferred from cells.

If writer maintenance provides cheap reader completion but increases mixed-trace cost for write-heavy/short-lived workloads, report the tradeoff and break-even condition. If it dominates the relevant read-heavy fixed-hash traces, abandon any broad claim that compiled retry is operationally preferable for this fixed SHA1 publication task. In either outcome, this does not invalidate a theorem restricted to the earlier action class, establish an application that forbids maintenance, or prove compiled better than a simple dirty threshold. The latter remains a separate unresolved comparator.
