# Public event-driven graph integration — exploratory input plan

Primary route SCIENTIFIC. This extends the fixed native source driver using the existing public EventDrivenUpdateGraph.requestRefresh API rather than directly invoking ControlledUpdateGraph's start/complete test controls. The existing official fixed-hierarchy/value-update example motivates the data shape, and the public EventDrivenUpdateGraph API supplies an application-owned finite refresh count. This combination is an author integration; a preexisting end-to-end application with refreshing K and V has not been found. The ordinary Web tree path uses static K and is not represented by the two-refreshing-stage comparison.

Each case creates an isolated EventDrivenUpdateGraph, registers one retained source Runnable, and issues at most q requestRefresh calls from a dedicated writer thread. Each call starts one native update cycle, executes sources and notifications, and completes it. For START, the registered source signals entry (after the real cycle starts) and waits before updating values. COMPLETE releases that same source and waits for the same requestRefresh call to finish. FULL invokes one requestRefresh without a pause. No direct clock/test cycle mutation is used. All pauses are author scheduling controls and are excluded from selected-operation cost. The source and key structure, Exact Sentinel/Action modifications, K4/V104 cap proof, owned chunks, strict hooks and output validation are unchanged.

Inputs: lambda3, four previously observed scripts {none, v_end_split, cross_stage, k_full_v_split}, and policies {curve_fast_tie, local_budget, upstream2}:12 cells. The existing all-budget profile_3 bytes from deephaven_prefix_import_02 are reused unchanged, loaded by Java only for the curve policy. This is not a new compiler benchmark or held-out input set. The same-phase finite-DP experiment is separate and is not used here.

The cap on refresh requests gives q without assuming a naturally finite Periodic graph. Returned chunks need one consistent epoch within the admitted execution, not the final value after all possible refresh requests. As in the original scripts, policy termination/protection may suppress later requests; q is an upper bound, and realized update counts must be reported. No equal-realized-workload elapsed-time comparison is claimed.

Before outcomes, preserve Java/checker/profile/core source bytes and the source-bound application report. Run once with180s process and30s case timeout; retain every SUCCESS/FAILURE/TIMEOUT/INVALID/missing cell, including construction failures. Writer cleanup releases a paused source, joins/stops its executor and stops the graph. The source hooks are unchanged from the previous successful10 regressions; fresh compilation and new-case conformance are the relevant additional checks.

Falsifiers: inability to execute with the public graph; inconsistent/misordered output; more refresh requests than q; unrecorded native clock transitions; failure count above2q; prefix counters above4/104; or imported-policy charges above the all-budget value. A failed input/setup will be preserved and corrected only in a separately recorded attempt. Success supplies an API composition example with explicit finite budget, not production prevalence or broad optimality.
