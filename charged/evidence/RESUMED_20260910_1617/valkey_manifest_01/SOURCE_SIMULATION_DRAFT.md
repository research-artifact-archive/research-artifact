# Atomic manifest source correspondence

Author proof draft for the specific client/writer/Lua API in this directory. It is not a theorem about all Valkey applications or an upstream bounded-retry algorithm. The source pin and unmodified binary are fixed in SOURCE_FETCH.json and BUILD02_RESULT.json. The scalar controller compiler and native traces are corroboration, not substitutes for this argument.

The concrete data state is a hash containing strings(v_i,b_i), with |b_i|=s_i fixed. The trusted writer's increment_decimal is addition of1 on a canonical nonnegative decimal string: each digit is processed right-to-left, carry is0/1, and a final carry prepends1. No full version is converted to a Lua double or signed64-bit counter. All previous versions are therefore unequal to the new one within the admitted no-reset/no-eviction execution. writer.lua verifies every update's existing length and computes all replacement fields before its sole HSET; one call changes precisely its declared nonempty footprint. Valid schema, available memory, normally completed commands and exclusive use of this writer API are contract assumptions. Atomicity does not generally imply rollback after script errors.

An initial/next preparation reads all version/blob pairs in one HMGET. Its atomic response captures a consistent source snapshot; immutable client copies determine its component digests. The abstraction maps that snapshot to a fresh full preparation. Client hashing can overlap later writes: its result depends only on immutable captured bytes, so placing its abstract preparation at snapshot capture and representing later writes in that attempt preserves its final prepared result. Outside transform work is grouped at preparation completion, with a temporary counter for an unfinished hash if instruction-level accounting is required.

Between this snapshot and step.lua's protected version read, each admitted writer call changes exactly one declared footprint and strictly advances every affected version. Hence the returned comparison mask is exactly the union of those footprints, including overlapping and repeated writes. A write which preserves content still invalidates its version and is deliberately counted dirty. Absence of version reuse prevents two writes from falsely appearing clean. Conversely, any finite allowed footprint word can be realized after each fresh snapshot by these writer calls, without a write inside the atomic validation. Fixed shapes and supported footprint families make the observation family and its least realizing counts history independent.

Within step.lua, atomic script execution excludes concurrent data changes from current-version read through the final publication. The policy action is selected here, not by a second client round trip after a dirty result. Its input contains the configured finite family, cap state t, least-history state e and compiled table, but no actual or future budget B. The trusted client decreases t only on reject, refreshes the preparation, and invokes at mostq validations. A last-call action must accept; the script asserts rejection has t>0. This is a client-library contract, not server-side multi-client quota enforcement or a guarantee after reply loss/reconnection.

For each clean component, equality of versions and content immutability imply that the prepared digest is the current payload digest. For each dirty component, the script hashes exactly the current blob under the same atomic protection. Therefore the assembled version/digest vector equals the live data at its final SET. Every input validation, hash and JSON encoding occurs before that sole publication. A reject does no SET and returns no completed result. The accept return is encoded before publication, then returned unchanged. A later external write changes the data but not the operation's historical linearization result; current forever is not claimed. If a caller requires security authentication or collision resistance beyond equality of computed outputs, that is another contract.

At completed validation boundaries the observed payload-byte resource is exactly

    L_payload = sum_{i in accepted dirty set} s_i,
    W_payload = P * Q_validation + L_payload, P=sum_i s_i,
    Q_wire = Q_snapshot + Q_validation = 2 Q_validation.

Only one validation accepts, so server payload hashing is entirely in that call. These are bytes supplied to the selected component transform, not total CPU instructions, SHA1 compression calls, whole-script work or latency. In particular8/16/24-byte payloads all fit a single padded SHA1 block; input-byte weights must not be presented as different measured compression-round counts. Script loading/caching, Lua parsing and policy-table transfer, version scans, blob reads/copies, encoding/SET, GC and external writer work remain outside this limited transform measure. Wire request/response bytes and command classes are separately retained in the native logs. The native test totals include setup/oracle/writer commands distinctly and do not pretend the test harness costs equal the foreground request costs.

The operational result maps to the single-job partial-repair interface: fresh prepare; a finite hidden footprint word; dirty observation and repair/reject in one protected validation; permanent request completion at publication. Native comparison decisions use the same action table whose history clipping is separately justified by the abstract model. This correspondence makes the scoped theorem applicable to this author API; it does not establish that the source offers no stronger operation. full_server.lua completes the exact same publication in one validation without any preparation. Its cost is L_payload=W_payload=P, Q_wire=1. Optional subsets, batching, writer-maintained transforms and different application completion contracts need explicit treatment before claiming a broad native optimum.
