\subsection{Why the Generated State Represents the Contract}
\label{sec:contract-adequacy}
A \emph{local update history} is $\ell=z(a_1,o_1)\cdots(a_n,o_n)$, starting at a reachable old closed-loop tuple $z$; each $o_j$ records all realized local successors. Ordinary events preserve versions; a transfer changes only its component to the realized new-version state; boundaries preserve physical states. Active monitor memories are folds: ordinary events/transfers advance every active monitor; stop advances the other active monitors and removes its own without consumption; start advances existing monitors before installing its initializer. Other inactive monitors stay inactive. Initially inherit old memories, initialize interval monitors, leave new monitors inactive and release old control.

An ordinary event requires all participating components' local edges; all their outcome combinations remain possible. Commands require UC quiescence, unexecuted status and completed predecessors; transfers also require a $g_i$ outcome and starts an initializer value. Count UC events even if their monitor outcomes are unsafe. A source policy selects controllable labels, retaining every enabled UC and every permitted outcome. It wins when every maximal history safely reaches a UC-quiescent matching target after all commands, without deadlock or an infinite run. These history operations induce the game state; their full recurrences are in Technical Appendix~\ref{ta:source_synthesis}.

\begin{proposition}[Adequacy of the generated update game]
\label{prop:contract-adequacy}
For an eligible contract, map each local update history to its current component tuple, active monitor memories and unexecuted commands. Histories with the same image admit the same next events and all the same local outcomes, agree on safety, and have the same handover targets. This map gives a label- and outcome-preserving correspondence between local update histories and paths of the generated game. A history-dependent policy satisfying the source obligations exists exactly when a winning policy exists in that game.
\end{proposition}
For start, both descriptions advance existing monitors, install the same initializer value and consume one command. For transfer, each $g_i$ outcome yields exactly its installed new state; neither representation selects the outcome. The other cases and policy transport preserve safety, deadlocks and completion (Technical Appendix~\ref{ta:source_synthesis}). This concerns the supplied contract; requirement meaning and Java frontend correctness are separate obligations.
