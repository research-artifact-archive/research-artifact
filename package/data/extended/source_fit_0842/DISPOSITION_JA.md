# 実caller調査の範囲と帰結

著者側担当はBookKeeper、Vaelii、Luceneの3アプリケーションを限定調査した。親担当は6 exact-commit一次sourceを取得し、全byte hashが担当報告と一致することを確認した。親担当が直接読んだ範囲はBookKeeper addEntry/WriteCache.put、Vaelii opt-read/match-one/place-fact-conclusion、Lucene tryPopulateCacheである。全repositoryを親担当が再走査したとは扱わない。コード実行・実測は行っていない。

BookKeeperには楽観的なforeground挿入からread lock下の再実行へ切り替える実操作があり、モード選択の動機として肯定的である。一方、投機的挿入はoffset予約、copy、index/counter更新を既に行い、fallbackは同じentry byteを再利用する。後続LAC更新との順序はあるが、現契約の純粋kernel出力を捕捉する依存DAGではない。cache full/timeoutもあるため、現在の定理をこのコードの最適性へ直接移さない。

Vaeliiではpure bodyを検査後に返し、不整合時read lock下で再実行する実装がある。これは純粋読取りの再実行と保護の動機を与える。しかしbelief read後のunificationや結論保存はそのretry bodyの外であり、既存record・conclusion・justification再利用も実装されている。これら全体を一つのwhole-kernel retryへ置換すれば新しいprotocolの設計になる。Luceneはcache計算後にputIfAbsentし、競合時に再計算せず既存結果を再利用する安い比較例である。

有限B、固定仕事量、保護価格は抽象化として宣言でき、sourceにその数値がないだけで動機を否定しない。今回なお未確立なのは、依存する必須変換、捕捉された前工程出力、whole-work反復、および検証と結果公開を結ぶ契約の実caller適合性である。二つの実操作の動機を完全な用途検証へ昇格させない。3候補の限定探索で用途一般の不存在も主張しない。
