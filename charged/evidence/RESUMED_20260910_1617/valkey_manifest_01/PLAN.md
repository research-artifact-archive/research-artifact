# Valkey current-version manifest publication: exploratory feasibility01

Recorded before implementation and execution. This is an author-built application API on a pinned unmodified Valkey8.0.2 server, not an upstream retry algorithm, production deployment, or final evaluation. The decision is whether a concrete atomic API can implement the partial-repair observation/action/completion contract with an exact, explicitly limited resource unit. Practical necessity and closest-work novelty remain separate open questions.

Pin d6a2f561e2751d4ab246ad084e4fa185526fa479. Download and hash the source archive, build an isolated server, run only on a private Unix socket with TCP disabled, no persistence and no external clients. Bound every subprocess and close the owned server on exit. Keep build failures and all attempted cases. No paid API, external account changes, or user data.

One request publishes a vector of component versions and SHA-1 digests matching the live data at the publication command inside an atomic Lua call. SHA-1 is a deterministic payload transform for this feasibility experiment, not a cryptographic security claim. Components have fixed byte lengths. A trusted writer API atomically replaces exactly a declared footprint and changes a decimal-string version for each replaced component. Versions compare as strings; no expiry, eviction, deletion/recreation, alternate writer, failure/reconnection, or version reset is in the admitted execution class. Dirty means version mismatch even for a content no-op. A client obtains every version/blob pair in one atomic HMGET and hashes its immutable local copies; subsequent writes can be represented as occurring after this snapshot. Every attempt prepares afresh.

The EVALSHA validation reads the versions, computes D, and chooses reject or repair inside the atomic script using a policy table and past observations supplied by the trusted single client. The controller receives no write budget B. On accept it hashes each dirty payload once, reuses clean prepared digests, validates/encodes before the final single publication SET, and returns the result. The last permitted validation must repair and complete. Returning dirty to the client before making the decision is forbidden. Reject performs no publication and may return a trace, but does not silently perform the next fresh read. Policy state remains per-request client memory; lost replies and multi-client quota enforcement are excluded.

Resource boundary: L_payload is bytes supplied to redis.sha1hex for component payload transformations inside accepted validation; P=sum component bytes is freshly hashed outside on every attempt; W_payload=P*Q_validation+L_payload. This excludes version scans, argument serialization, copying, SHA script management, Lua allocation/GC, publication, replication, and writer work, all disclosed. Q_wire foreground equals Q_validation+Q_snapshot, normally2Q_validation, with SCRIPT LOAD and setup separately counted. No claim that L_payload bounds whole script time, maximum blocking per call, or an SLA. A later latency experiment would require its own plan.

Implement a deterministic fixture explorer with independently recomputed digests and traces: fixed component-size vectors(8,16) and(8,16,24), singleton and one declared batch-footprint family, q=1,2,3. Compare immediate repair, reject-positive-until-last, and an extracted minimum-uniform-regret policy for supplied abstract toll values0,8,24. All policies have the same preparation/action class and call cap. Enumerate all observation words of length at mostq for these small finite families, stopping a word when the policy completes. Retain every row including duplicate prefixes; distinguish raw trace count from unique execution count. Verify publication against current versions/blobs, independently recompute dirty from previous/current versions, check no reject publication, exact hash-byte sums, per-policy cap, and the predicted whole curve/maximum additive regret when all minimum-cost observation words are enumerated. Record actual complete denominator in the frozen INPUT_MANIFEST before executing.

Include semantic negative controls: intentionally corrupt a returned digest, dirty mask, hash-byte count, and reject/publication status; the independent checker must reject them. Include large decimal versions above2^53 and2^63, content-preserving writes, overlapping/repeated footprints, and a late change after publication that does not retroactively invalidate linearization. These are separate tagged development controls. Implementation defects are failures of this version and repaired under a new attempt with reasons.

Strong alternatives are not excluded by fiat: a one-call all-server computation can avoid preparation; one HMGET plus client hashing suffices for snapshot return but lacks current-version publication; WATCH/MULTI/EXEC implements all-or-nothing validation but has different call/fallback semantics; writer-maintained digests may dominate for this fixed transform. This exploration will implement/quantify the first two cost alternatives and document that writer maintenance is a live alternative. It will not infer universal Redis optimality from the restricted policy class. A read-only author survey separately checks actual conditional-publication uses and whether request-dependent transformations are necessary.

This is exploration, not a pre-registered empirical performance claim. Before any paper adoption, state-level simulation and source-cost arguments must be written, checks extended/fixed as needed, and independent contextual critique obtained for a substantively changed paper.
